# Structural Escalation Protocol

If execution reveals a problem requiring change to Core Question, Claim Type, Evidence Architecture, key construct, primary evidence, geography, sample population, central claim, Paper Scope, or any causal design object, stop the affected branch and report: OBSERVED PROBLEM; EVIDENCE; AFFECTED GATE; AFFECTED DESIGN OBJECT; IMPLICATION; OPTIONS; WHICH OPTIONS CHANGE DESIGN; RECOMMENDATION; DESIGN DISCUSSION REQUIRED: YES. Do not silently redefine geography, construct, treatment, outcome, counterfactual, estimand, identifying assumption, or instrument.

Executor access failure alone is not a structural research-design escalation. Route it through `protocols/data_access_handoff.md`; escalate scientifically only if validation or true team-level unavailability threatens a frozen design object.

For material scientific-object drift, use `protocols/research_genesis_branch_governance.md`: compare Genesis Anchor, current branch fingerprint, and Scope Contract; propose IMPLEMENTATION REPAIR / DESIGN REPAIR / EXTENSION / NEW BRANCH / BRANCH REPLACEMENT; preserve the parent record and link `templates/SCOPE_CHANGE_MEMO.md` where applicable. This makes existing structural escalation explicit, without adding a STOP condition or changing authority. Routine approved implementation repairs need no unnecessary branch or scope approval. A valuable parent must not disappear for execution convenience, but a scientifically failed branch may be explicitly killed. Material replacement, causal downgrade, or split requires existing Research Director review and PI decision; new branches inherit no automatic claims, Gate decisions, or scope approval.
